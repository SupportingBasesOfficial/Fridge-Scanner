# FridgeScanner — DB-02 Physical Decision Register

## Status

Working physical-decision register for DB-02. These decisions implement accepted DB-00/DB-01 semantics; they do not reopen them.

## P-001 — PostgreSQL major baseline

**Decision:** target PostgreSQL 17.x as the minimum initial production/self-hosted baseline; avoid unnecessary 17-only constructs so the schema remains forward-compatible with PostgreSQL 18.

**Reason:** PostgreSQL 17 is a current supported upstream major and aligns with the current Supabase platform/self-hosted default while retaining standard PostgreSQL portability.

## P-002 — Primary key type

**Decision:** application/domain row identifiers use UUID, generated by the trusted mutation boundary. Physical schema does not assign semantic ordering meaning to UUID values.

**Initial generation:** UUIDv7 is preferred where the runtime/database capability is explicitly available and tested; otherwise cryptographically strong UUIDv4 is acceptable. The PK contract is UUID, not one UUID version.

**Reason:** stable distributed identity without provider sequence coupling; UUID version may evolve without changing domain identity semantics.

## P-003 — Exact rational quantity encoding

**Decision:** authoritative rational quantities are stored as normalized signed numerator + strictly positive denominator using PostgreSQL `numeric` integer semantics, not fixed-width integers and not decimal approximations.

Physical pair:

- `quantity_num numeric NOT NULL` constrained to integral value;
- `quantity_den numeric NOT NULL` constrained to integral value and `> 0`;
- pair normalized so gcd(|num|, den) = 1 where committed through trusted routines.

Zero is canonicalized as `0/1`.

**Reason:** DB-00 explicitly requires lossless representation for values such as one third; arbitrary-precision `numeric` integers avoid overflow assumptions and decimal truncation.

## P-004 — Rational normalization enforcement

**Decision:** authoritative writes of rational pairs pass through one canonical SQL normalization function or equivalent trusted mutation routine. Direct application DML to authoritative quantity-bearing history tables is restricted.

**Reason:** PostgreSQL CHECK constraints can enforce denominator/integrality but cannot cheaply guarantee gcd normalization everywhere without function support.

## P-005 — Money encoding

**Decision:** authoritative monetary amount uses `numeric` with a governed currency code, semantic role and source/derived provenance. `money` type and floating-point types are forbidden.

Currency-specific scale/rounding policy is applied only at governed monetary boundaries; source values preserve their authoritative scale/provenance where required.

## P-006 — Currency identity

**Decision:** currency code is a constrained textual ISO-style code or FK to governed reference data; no numeric amount exists without currency identity when the fact is monetary.

## P-007 — Enum strategy

**Decision:** stable, closed infrastructure states may use PostgreSQL enums only when removal/renaming is not expected. Domain classifications expected to evolve use governed reference tables or constrained text + reference data rather than hard-coded enums.

**Reason:** avoids turning schema migrations into the ordinary editing mechanism for extensible business taxonomy.

## P-008 — Household structural enforcement

**Decision:** high-risk Household relations use direct `household_id`. Parents expose composite candidate keys `(household_id, id)` where needed; children use composite FKs `(household_id, parent_id)` to prevent cross-Household attachment at the database layer.

**Reason:** RLS alone is not relational integrity and application filtering cannot repair a structurally invalid cross-tenant link.

## P-009 — Global/Household catalog ownership

**Decision:** catalog tables persist `catalog_scope` plus nullable `owner_household_id` and use CHECK constraints for GLOBAL XOR HOUSEHOLD ownership. Cross-scope reference rules that require visibility logic are enforced through constrained transactional routines and, where practical, composite/partial uniqueness.

## P-010 — XOR relationships

**Decision:** fixed alternative relationships use explicit nullable typed FK columns plus CHECK constraints enforcing the required XOR/cardinality. Generic `target_type/target_id` is prohibited for referentially significant business relationships.

## P-011 — RLS posture

**Decision:** enable RLS on Household operational tables and Household-private catalog rows. Policies rely on a trusted per-transaction/session principal/Household context established by the API boundary. Service/maintenance roles are separate and never implicitly used by normal client traffic.

**Rule:** RLS cannot be the sole enforcement of cross-row Household equality; relational constraints remain mandatory.

## P-012 — RLS fail-closed context

**Decision:** missing or malformed application authorization context yields no Household access. Database helpers that read trusted context are `STABLE`, schema-qualified and do not infer authority from arbitrary client-supplied row values.

## P-013 — Immutability mechanism

**Decision:** authoritative history/evidence tables deny ordinary UPDATE/DELETE to application roles. A shared trigger/function guard provides defense in depth for roles that can otherwise reach those tables. Governed correction is append-only.

## P-014 — Multi-row invariant enforcement

**Decision:** conservation, allocation-pool limits, transfer pair creation, preparation accounting, count reconciliation and similar multi-row invariants are committed through transaction-safe database routines and/or deferred constraint triggers. Ordinary client DML is not permitted to assemble a half-valid business operation across statements.

## P-015 — Transaction isolation

**Decision:** invariant-sensitive routines lock the smallest stable aggregate/resource set needed to serialize competing writers. `SERIALIZABLE` may be used for operations where explicit locking would be error-prone, with bounded retry at the service boundary. Global SERIALIZABLE-by-default is not required.

## P-016 — Inventory ledger

**Decision:** `inventory_movement` is append-only authoritative quantity history. Current balance is a derived projection/view/materialized table and never a writable competing truth.

## P-017 — Current-balance materialization

**Decision:** initial physical contract permits a recomputable balance projection maintained transactionally or asynchronously only if staleness semantics are explicit. Authoritative mutation validation must use committed ledger truth or a transactionally equivalent locked aggregate, not an eventually consistent cache.

## P-018 — EffectiveExpiration materialization

**Decision:** EffectiveExpiration is a recomputable projection with derivation/version/status and candidate provenance. It may be stored for reads but can be invalidated/rebuilt from authoritative source/rule/lineage evidence.

## P-019 — Time representation

**Decision:** authoritative instants use `timestamptz`. Local calendar source values retain their original local/date precision separately where DB-00 requires it. IANA timezone identifier and selected governed timezone-version identity are persisted independently; server/session timezone is never historical business evidence.

## P-020 — Date-only expiration

**Decision:** source date-only expiration remains `date` + source precision/semantics. Any operational instant derived from it is stored only as derived evidence/projection with the exact timezone selection provenance required by DB-00.

## P-021 — Identifier normalization

**Decision:** canonical normalized identifier values are persisted with normalization-rule identity/version and exact source value. Uniqueness uses scoped partial/functional indexes reflecting global-vs-issuer namespace semantics; private staged claims never participate in canonical global uniqueness.

## P-022 — JSON boundary

**Decision:** `jsonb` is allowed only for opaque provider payload fragments, non-authoritative diagnostic context or versioned message payloads whose internal structure is not relational business truth. Household topology, money, quantity, ownership, typed subjects and invariant-bearing relationships must not be hidden in JSON.

## P-023 — Outbox encoding

**Decision:** Outbox stores contract identity/version, business identity/scope, publication state and a versioned payload (`jsonb` acceptable). The payload is derived publication material, not a replacement for normalized authoritative business rows.

## P-024 — Audit target metadata

**Decision:** AuditEvent may retain generic target type/stable identity as evidentiary metadata because DB-01 explicitly permits it. This metadata never substitutes for typed business FKs in operational relations.

## P-025 — Index policy

**Decision:** every FK used in operational joins/lock paths gets a deliberate supporting index unless proven redundant. Tenant-leading composite indexes begin with `household_id` when primary access is tenant-scoped. Uniqueness indexes mirror exact domain uniqueness scope; speculative indexes are avoided.

## P-026 — Partial/exclusion indexes

**Decision:** use partial unique indexes for conditional active/current uniqueness and exclusion constraints for non-overlapping effective intervals when core PostgreSQL can express the rule clearly.

## P-027 — Partitioning

**Decision:** do not partition by default. `inventory_movement`, `audit_event` and `outbox_record` are designed with partition-compatible keys/indexes, but physical partitioning is introduced only after measured scale/retention needs justify operational complexity.

## P-028 — Deletion semantics

**Decision:** authoritative/history rows do not use cascading physical deletion from mutable business parents. Referential actions default to RESTRICT/NO ACTION for history. Lifecycle deactivation/retention workflows are explicit. Cascades are reserved for strictly dependent transient/configuration rows where loss cannot erase audit/business truth.

## P-029 — Migration tooling contract

**Decision:** migrations are plain ordered SQL as the canonical database migration source. A framework may orchestrate them later, but correctness must not depend on ORM-generated schema state.

## P-030 — Migration direction

**Decision:** production changes are forward-fix by default. A migration may include a safe down path only when truly reversible without loss; destructive rollback is never implied. Backups/PITR and tested forward repair are operational recovery mechanisms.

## P-031 — ORM boundary

**Decision:** ORM selection is deferred to backend architecture. The ORM must map to the database contract rather than generate/redefine it. Database constraints/functions/RLS remain authoritative.

## P-032 — Security-definer functions

**Decision:** `SECURITY DEFINER` is deny-by-default. When unavoidable, function owner, `search_path`, parameter validation, grants and RLS behavior are explicitly reviewed; public EXECUTE is revoked.

## P-033 — Schema namespaces

**Decision:** canonical application tables/functions live in explicit application-owned schemas rather than relying on an uncontrolled default `public` namespace. Provider-managed schemas remain separate. Exact namespace names are fixed by the SQL baseline before migration acceptance.

## P-034 — Extension posture

**Decision:** no extension is accepted merely for convenience. Core PostgreSQL is sufficient for the initial DB-02 contracts; any later extension requires an explicit decision recording portability, backup, upgrade and hosted-provider compatibility.
